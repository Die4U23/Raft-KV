# 第三组收尾测试：过载与有界持续运行

脚本与本地辅助检查已提供，真实 Linux 结果仍为 **UNRUN**。这是本轮收尾的最后一组，不追加新的长期压测任务。前两组原始证据已核验：分区与恢复、持续写入与节点重启。

## 测什么

| 阶段 | 负载与验收 |
| --- | --- |
| 连接准入 | 三节点设置 `--max_clients=32`。Leader 保留 1 条监控连接并占满另外 31 个名额，再尝试 5 条连接；必须被关闭且 overload_rejections 增长。释放后新连接 PING 成功 |
| 写入积压过载 | 暂时隔离旧 Leader 的 Raft 通信，以 24 个并发连接各发送一个 800 KiB 值。至少出现一个明确 BUSY，过载计数增长；采样中队列和提案条数/字节不越过实现上限 |
| 恢复 | 恢复通信，成功写入恢复标记，等待队列、待处理提案、输入/输出积压和应用滞后归零 |
| 固定键持续读写 | 2 个持久客户端反复覆盖各自的 64 个键，SET 后立即 GET 检查精确值；预热 10 秒，再采样运行 60 秒，无客户端错误 |
| 卸载后检查 | 停止客户端，核对三副本的全部 128 个键；再采样 10 秒，队列持续为空，只保留监控连接 |

通过需要所有阶段成功，不能因为“没崩溃”就跳过 BUSY 和过载计数检查。隔离阶段等待回复超时的写入保留为 unknown，不计入成功，也不自动解释为失败；本组对大值的重点是过载拒绝和资源释放，未知大键的存在性不属于此处的逐键核验，未知语义已在前两组专门检查。

连接阈值 32 是为了在小型 VM 上确定性地触发准入控制，不宣称已测出默认 1024 个连接的容量。C++ 源码、16 MiB 写队列/提案配额与同步持久化设置没有改动。

## 资源采样与判定边界

脚本读取自己启动的三个进程的 `/proc` 数据，保存每份 INFO、RSS、累计 CPU 时间、线程数、文件描述符数量与日志大小。预热后大约每秒采样一次。

本轮使用显式的宽松资源保护阈值：

- 稳态末 10 份 RSS 中位数比前 10 份增长不超过 32 MiB/节点。
- 同样窗口的文件描述符中位数增长不超过 8/节点。
- 所有阶段采样到的单节点 RSS 不超过 512 MiB。
- 持续读写至少有 30 份稳态采样；停止负载后积压清零。

这些是该测试的有限验收条件，不是生产容量承诺，也不能从 60 秒观察推断长期无泄漏。固定键避免 KV 键数持续增长，但 Raft 日志仍可能增长。CPU 汇总使用“100% 等于一个 CPU 核”的进程口径，不设 CPU 通过阈值。

第一组已经发现 TCP 建连后立即关闭会引发大量重连。本组仍记录隔离窗口中的转发拒绝次数与日志增量；拒绝次数超过 100 时打印 OBSERVATION，并在报告 warnings 中保留，不能因其他阶段 PASS 就宣称重连节流问题已经解决。本次没有改动服务的重连实现。

## Ubuntu 执行

更新到含脚本的版本，在项目根目录运行：

```bash
python3 tests/cluster_overload.py \
  --build-report build-linux-fresh-1vukPy/reports/run-a3q01rgw/build-report.json \
  --artifacts build-linux-fresh-1vukPy/overload-reports
```

通常约 90 秒，整轮期限默认 150 秒，清理有额外的有界等待。可以通过 `--soak-seconds` 选择 60～180 秒；本轮收尾使用默认值即可。无需 sudo、系统防火墙变更或重编译 C++，脚本运行前核对已有构建报告和实际二进制/编译输入指纹。

只管理测试自己的三个进程、转发器、随机端口和临时数据库。报告目录保留 report.json、三个节点日志、Git 记录以及 referenced-build-report.json。成功输出 `PASS: bounded Linux overload/soak test; report: .../report.json`；失败为 FAIL 与非零退出码。OBSERVATION 表示单独保留的资源观察问题，回传证据时一并提供。
