# 网络分区与失去多数派测试

这是实习展示收尾的第一组故障测试。用户回传的真实 Linux 原始材料已核验，**5 个阶段全部 PASS**，覆盖两次短时对称 TCP 分区与恢复；见[原始证据及边界](benchmarks/partition-validation.md)。本轮还有大量重连和日志输出，需要在后续资源测试中关注。

## 场景与判定

| 阶段 | 检查 |
| --- | --- |
| 正常三节点 | 通过转发通道选主，成功写入基准数据，三个节点提交和应用进度一致 |
| 隔离旧 Leader | 三个进程保持运行，旧 Leader 的客户端端口可用；它不能确认探测写入，提交和应用位置不前进；另一侧两节点选主并确认新写入 |
| 第一次恢复 | 恢复通信，成功写入恢复标记，所有节点读到已确认的数据 |
| 三个节点互相隔离 | 向每个节点各发送一次写入，均不得成功回复；观察窗口内所有节点的 commit_index、last_applied 不前进 |
| 最终恢复 | 不重启节点，恢复选主和新写入；已确认数据与结果未知请求的最终状态在三节点收敛 |

默认每个分区至少观察 4 秒，期间持续查询三个节点 INFO，并保存快照。返回 RESP 错误记为拒绝；成功发送之后等待回复超时记为“结果未知”。超时不撤销日志，恢复后该写入可以存在或不存在，但最终副本必须一致。连接失败、节点退出、异常回复、无多数派却成功回复或推进提交/应用都使测试失败。

客户端不重试探测写入，避免把一次不确定操作变成多次尝试。GET 仅用于恢复后的副本检查，不把现有本地读称为线性一致读。本测试是有限的进程级集成场景，不证明所有网络故障或 Raft 正确性。

## 如何隔离通信

`tests/raft_proxy.py` 为每个有向节点对建立一个独立的本地 TCP 转发端口，共 6 个。节点使用各自的 peers 配置，所有跨节点 Raft 消息都经过这些通道；客户端端口直连节点。

分区时关闭跨组的现有转发连接并拒绝新连接，组内连接仍可转发。恢复时重新允许建立连接，由服务自行重连。它模拟 TCP 断连/拒绝连接的对称分区，不模拟静默丢包、非对称分区、延迟或乱序。不需要 sudo，不修改 iptables，不停止网络服务或其他集群。

## 在 Ubuntu 执行

先更新到包含此脚本的版本。使用你已经完成全量构建的报告：

```bash
python3 tests/cluster_partition.py \
  --build-report build-linux-fresh-1vukPy/reports/run-a3q01rgw/build-report.json \
  --artifacts build-linux-fresh-1vukPy/partition-reports
```

无需为新增的 Python 测试重编译 C++。脚本启动前将实际二进制 SHA256、当前 CMakeLists.txt、src/proto 输入和固定 Muduo zip 与指定构建报告核对；出现不一致就停止，不能将旧二进制配上新源码继续测试。其他机器应使用自己的 PASS 构建报告路径。

成功时最后显示 `PASS: real Linux partition test; report: .../report.json`；失败为 FAIL 和非零退出码。整轮默认期限 90 秒，清理有额外的有界等待。不要手动杀死测试节点；脚本管理自己的三个进程、转发器、随机端口和临时数据目录，结束后保留日志和报告。

新报告目录包含 report.json、三个节点日志、Git 状态与提交记录，以及 referenced-build-report.json。JSON 记录二进制和本轮测试代码指纹、节点启动参数、分区拓扑、转发统计、INFO 快照、探测结果和恢复后的数据状态。保存整个报告目录以供核验。

```sh
python tests/cluster_partition_tests.py
```
