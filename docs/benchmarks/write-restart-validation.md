## 故障与恢复

1. 初始 Leader 为节点 0。强制退出前约 2.040 秒的写入窗口内，共确认 576 个键。
2. 序号 576～583 的 8 个请求完成 sendall 后、读取回复前，节点 0 被 SIGKILL。该批全部记为未知；这是客户端尚未读取回复的证据，不推断当时服务端是否已提交。
3. 节点 2 成为 Leader。旧 Leader 停止约 2.184 秒期间，客户端仍持续尝试，并收到另外 576 个成功确认。
4. 节点 0 从原配套目录重启。之后约 2.025 秒内再确认 552 个键，停止写入后设置核验标记，等待提交/应用追平。三个副本各检查 1,832 个尝试键及标记，全部满足结果判定。
5. 在写入线程已停止、第一次数据核验完成后，强制退出全部节点，再使用各自相同参数与配套目录启动。重复三副本逐键检查，所有已确认数据保留，未知请求的存在性与第一次核验一致。

节点 0 的退出记录为 -9、-9、-15，另两节点为 -9、-15。节点日志分别包含 3、2、2 次启动标记，与报告一致；最后的 -15 属于结束清理。

最终 Leader 为节点 1，三个节点任期均为 7，commit_index=last_applied=1709，pending_proposals、apply_lag、apply_inflight 均为 0。整轮记录耗时 15.265 秒，包括写入、恢复、核验及清理，不能当作恢复延迟或压测时间。

## 结论范围

本组确认该 VM、该二进制在本轮有限连续写入与进程崩溃恢复场景中，没有丢失客户端已确认的键。恢复检查由已匹配源码中的逐键断言执行，报告保留摘要与请求结果账本，没有逐次 GET 的原始回复转录；包中也没有二进制或数据库本体。

SIGKILL 不模拟整机断电或存储设备损坏；本地 GET 仍不提供线性一致读。请求超时不是失败或取消，未知键不存在只是本轮恢复后的事实。本轮不证明长期资源稳定性，不补充新的性能提升结论，也未在 Windows 重跑真实服务。
