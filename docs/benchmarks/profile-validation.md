## 测量结果

同一台双核 Ubuntu VM 上运行三个节点和一个 Python 3.14.4 客户端。32 连接，pipeline=1，128 字节 value，50% SET / 50% GET；预热 10,000 次，正式 100,000 次。服务端 `async_apply=true`、`group_commit_ms=1`，同步持久化设置不变。

| 指标 | 实测 |
| --- | ---: |
| 正式成功 / 错误 | 100,000 / 0 |
| 正式耗时 | 19.433 秒 |
| 成功吞吐 | 5,145.92 次/秒 |
| 批延迟 P50 / P95 / P99 | 5.242 / 14.631 / 21.663 毫秒 |
| 客户端 CPU | 12.22 CPU 秒，约占单核 62.88% |
| Leader CPU | 11.43 CPU 秒，约占单核 58.81% |
| 两个 Follower CPU | 单核 16.77% / 16.05% |
| 整机平均 CPU 空闲 | 4.97% |
| 整机 user / system / softirq | 64.52% / 23.71% / 6.80% |
| 正式窗口内外部采样 | 38 条（完整记录共 46 条） |

CPU 起止窗口约 19.434 秒，包含少量边界采样开销。正式吞吐窗口不含预热、连接建立、预填充与关闭连接。pipeline=1，所以每个完整批次只有一次操作；原始逐次延迟未归档，分位数只能核对报告值及样本数，不能从原始延迟重新计算。

日志写入与 KV 应用平均每批约 8.80 / 8.82 条。阶段统计单位不同、区间可能重叠，不能将各平均耗时相加当作请求总延迟。

## 正确性与结论边界

Leader 为节点 0、任期 2，正式测量期间保持稳定；正式写计数差分为 50,000。结束后每个副本验证 32 个正式负载键，三节点 commit/applied 均为 55,065，待处理提案和应用落后为零；三个进程均只启动一次并由测试清理。

CPU 余量很小，客户端也是同机资源竞争的一部分；目前没有函数级热点证据，不能说它是唯一瓶颈。日志写与 KV 应用的平均耗时不足以支持立即引入复杂存储缓存。下一步用[客户端头部合并读取对照](../optimizations/client-overhead.md)检验一个小范围开销改动。

不把本轮 5,146 次/秒与旧版约 3,800 次/秒直接计算优化收益；二者不是同条件交替对照。GET 仍是本地读，本报告不证明线性一致性、独立服务端容量或生产可用性。
