四轮正式窗口内采样分别为 28 / 27 / 33 / 31 条，完整采样分别为 34 / 31 / 37 / 36 条；CPU 起止差分排除预热。整机平均 CPU 空闲分别约 3.21% / 2.86% / 3.64% / 3.25%，资源竞争仍明显。

## 正确性与取舍

四轮共 400,000 次正式请求全部成功，错误为零；每轮预热也零错误。正式写入完成计数与本地读计数差分均为 50,000。各轮 Leader 任期均稳定在 2，每轮结束后每个副本验证 32 个正式负载键，commit/applied 均收敛到 55,065，写队列、待处理提案与应用落后清零。12 个服务进程各启动一次，由测试正常清理。

本轮没有观察到合并读取降低 CPU 或提高吞吐的收益，因此不切换默认模式。第 2、3 轮采用相同模式且 Leader 相同，吞吐仍下降约 19.56%，说明波动足以影响小幅差异的解释；不能据此认定合并模式在所有环境下必然更慢，也不能挑选第 2 轮单独宣传提升。

本次只改变客户端解析路径，不是服务端容量对照。新一轮 classic 本身已高于[先前单轮诊断](profile-validation.md)，不能把跨轮环境波动算成优化收益。GET 仍是本地读，报告不证明线性一致性、独立服务端容量或长期稳定性。

本实验至此收尾，不继续重跑同配置挑选结果。后续优化应先取得函数级热点或隔离客户端争用的证据，再选择服务端改动；这些工作尚未完成。
