# Raft-KV 实习项目升级路线

初始评估日期：2026-09-05；测试证据更新：2026-09-09。目标岗位：C++ 后端 / 基础架构。

## 项目定位

建议定位为“基于 Raft 的分布式 KV 存储与可靠性工程实践”。当前值得继续做，但尚不足以宣称生产可用。保留原项目出处，明确自己的改造范围；项目已有代码不自动等于个人贡献。

适合围绕配置数据、服务元数据的小规模可靠存储讲解应用场景。这是建议的场景定位，不代表已经实现配置中心、服务发现或分布式锁。

## 第二阶段：形成个人技术亮点

### 优先亮点一：批处理、异步应用与过载保护

已有实现可以作为研究基础。读懂从请求入队、日志持久化、多数派确认到状态机应用、返回客户端的完整路径，说明线程归属、回调生命周期与队列上限。

对比 async_apply 开关，两组保持相同硬件、数据、连接数和 sync=true。先用 pipeline=1 测单操作延迟，再单独测流水线负载。报告成功吞吐、错误率、p50/p95/p99、CPU、磁盘及 apply_lag；每组至少重复三次并保存原始数据。这是建议的完整验收条件。[当前四轮基线](benchmarks/ubuntu-2cpu-abba.md)按异步→同步→同步→异步执行，每种模式两轮，含 CPU 和前后 INFO 差分，原始材料已归档核验；还没有完成上述全套验收。当前停止追加相同配置测试，优先固化构建流程、在新测试中即时记录身份，并设计隔离客户端 CPU 争用的实验。

注意：group_commit_ms=0 仍可能合批，不能直接当作“关闭批处理”；现有压测工具在 pipeline>1 时统计整批延迟，不能把它写成单请求延迟。Raft 日志写入和本地 GET 仍可能阻塞事件循环，因此异步应用不保证性能一定提升。

### 优先亮点二：线性一致读

当前 GET 直接读取本地状态机，leader_only_reads=true 也不提供线性一致性。可以增加明确的本地读与强一致读模式，并实现 ReadIndex 路径：本任期提交前置条件、多数派确认、等待 lastApplied 达到读屏障，以及任期变化和超时处理。

验收场景：隔离旧 Leader，剩余多数派选出新 Leader 并完成写入；旧 Leader 不得成功返回过期的强一致读结果。再检查应用落后、领导权变化与并发读写历史。有限测试通过不等于完整正确性证明。

原理参考：[Raft 论文第 8 节](https://raft.github.io/raft.pdf)、[etcd API 保证](https://etcd.io/docs/v3.6/learning/api_guarantees/)。

### 后续亮点：请求超时与去重

明确区分“被拒绝”“成功”“结果未知”。断连或超时不能撤销已经复制的日志。设计客户端标识、请求序号、持久化去重结果及清理规则，并让去重状态随共识复制；仅在某个 Leader 的内存里保存请求 ID 不够。

验收：提交后丢失响应，客户端向新 Leader 重试同一请求，业务操作不会重复生效且返回约定结果。现有 DEL 的返回值就能帮助暴露重复执行问题。

## 简历与面试交付

每项个人贡献准备一页材料：原始问题、复现方法、原因、方案、测试结果、限制。只写本人实际完成且能解释的改造，不编造公司经历、上线用户、可用性百分比或性能提升。

完成相应工作后，可按以下句式整理：

“基于开源 Raft-KV 开展工程化改造，负责【具体模块】；针对【可复现问题】实现【方案】，通过【测试及环境】验证【结果】。”

量化性能时填写实测环境和数字；没有测量就描述机制。建议准备一个五分钟演示：启动三节点、写入并查询、终止 Leader、发现新 Leader、检查已确认数据、恢复旧节点、展示应用追赶和监控。

必须讲清的追问：

1. 为什么写入需要多数派，客户端成功响应发生在哪一步？
2. commit_index 与 last_applied 为什么不同？
3. 只读 Leader 为什么仍可能读到旧数据？
4. 批处理为何可能提高吞吐，同时增加低负载延迟？
5. 工作线程如何保持应用顺序，停止时如何处理未完成回调？
6. 超时后为什么不能简单认定写入失败？
7. 测试替身能证明什么，不能证明什么？
